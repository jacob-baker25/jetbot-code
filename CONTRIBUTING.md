# Team workflow for the JetBot

## Branches and responsibility

- `main`: reviewed integration code. It is not automatically a hardware-qualified release.
- `experiment/scan-gate-diagnostics`: existing experiment history; do not rewrite it.
- `imu-heading-log`: existing teammate contribution; preserve it for selective review.
- New work: one branch per task, based on an explicitly agreed commit. Current
  offline translation investigation: `analysis/stationary-sequence-replay`, based
  on `ee19f72` (coarse-level repair). No one else should push to this task branch.
- Each contributor uses a separate clone/worktree. Do not share a writable checkout.

Open a pull request for each task. State the base commit, problem, tests, hardware
evidence, limitations, and deployment/rollback procedure. For dependent work use
the experiment branch as PR base; do not merge all experimental history into main
as a side effect. Integrate the experiment branch into main separately after review.
No force pushes to shared branches. One teammate reviews changes to shared files
such as mapping_session.py, the IMU publisher, and deployment scripts.

Before starting a task (old Jetson Git compatible):

```bash
git status --short
git rev-parse --abbrev-ref HEAD
git fetch origin
git checkout -b YOURNAME/TASK AGREED_BASE_COMMIT
```

Do not pull a different feature branch into your current feature branch. A failed
fast-forward is a reason to inspect branches, not reset or overwrite local work.
If `git status` shows edits, preserve them on their existing branch first.

## Robot deployment

Treat the robot checkout as deployment-only. Make source changes on individual
laptops, commit and push a task branch, then deploy an exact reviewed commit.
Use a separate checkout for another person's experiment rather than switching
the checkout of a running process. Coordinate one robot operator at a time.

Record `git rev-parse HEAD`, source hashes, parameters and executable checks in
each run. A successful pull does not rebuild installed C++ code. Use the guarded
deployment script and build only the affected package with `--base-paths src`.
Never delete build directories underneath a symlink install.

Label a commit as hardware-qualified only after a completed run meets the stated
criteria. Timing PASS, stationary PASS, map geometry PASS and navigation PASS are
different qualifications. Keep the last qualified commit and experiment archive.

## Teammate heading contribution

Commit `2ebef5f` adds useful heading reports and optional `imu_yaw_hold`. Port the
reports selectively into offline laptop analysis with measurement-time checks.
Do not wholesale replace newer session/publisher files with those versions.
The gyro hold mistakes slow constant turning for stationary bias; keep it off
until an independently justified stationary condition and slow-motion tests exist.
Commanded stop alone is not proof of physical stillness.

Exclude generated bytecode, notebook checkpoints, build/install trees and large
experiment archives from code PRs. Keep raw results locally and retain hashes and
small analysis reports in reviewable documentation. Never erase a teammate's
uncommitted work merely to make status clean.
